# Agent 插件开发通用模版

> 从 agent-model-router 插件的完整开发周期提炼：格式探测 → 架构决策 → 可用性验证 → 防护闭环 → 发布协作。
> 方法论平台无关，代码示例以 ZCode 为对照实现。任何"给 Agent 平台写插件/技能"的场景可直接套用。

---

## 第一章 平台硬约束清单（先探明，再动手）

> 核心原则：**平台文档不会告诉你全部真相。动手写代码前，先把约束一条条探测清楚，否则后面全是返工。**

### 1.1 真实生效点 vs 提示词安慰

每个插件领域都存在一个"真实切换点"——平台运行时真正读取并生效的机制。在它之外的一切手段都是提示词安慰。

- **反面教材**：Agent 派发时在 prompt 里写"本 Agent 使用 XX 模型"——文字描述对运行时零效力，子智能体照跑主会话模型（假路由）。
- **真实生效点**：子智能体定义文件 frontmatter 的 `model` 字段，平台加载定义后按它路由。
- **通用问法**：我要控制的那件事，平台在运行时到底读什么？找到配置文件、字段、协议参数，把插件建立在它上面。

### 1.2 格式探测方法论

文档没写清的格式，用**探测链**锁定：错误格式 A → 观察报错 → 错误格式 B → 观察异常行为 → 对照平台自己生成的配置 → 锁定正确格式。

```
实测案例（model 字段）：
  尝试 A：builtin:xxx/GLM-5.3（slash 格式）→ 平台拒绝，无 API 调用
  尝试 B：GLM-5.3（裸模型名）→ 不报错但路由到错误的 provider（最危险：静默错误）
  对照：用户在设置界面手工配置后，读回配置文件 → custom:<provider_id>:<model_name>
  结论：让平台自己写一份正确样例，照抄结构，比反复试错快
```

**要点**：不报错 ≠ 正确。静默错误（如路由到错误 provider）比显式报错更难发现，验证时必须检查**实际生效对象**而不是只看有没有异常。

### 1.3 加载时机约束（决定架构的第一问）

问：我的插件在运行时生成/修改的产物，平台什么时候读取？

- 若平台**只在会话/进程启动时加载**（ZCode 子智能体定义即如此），则运行时生成的新产物在当前会话不可用，且没有任何 API 可强制重载。
- 这个约束直接决定架构形态（见 2.1），必须在写第一行代码前确认。

### 1.4 解析器陷阱

- 配置文件对"第一行"敏感：frontmatter 必须从文件第一行开始，之前哪怕一个 HTML 注释都会导致整体解析失败（`agent_missing_frontmatter`，且报错不指明真实原因）。
- **通用教训**：生成器写文件时，内容第一字符就是格式起始符，任何"美观性"前缀（注释、横幅、BOM）都可能炸掉整个解析。
- 排查手法：平台报"缺少 frontmatter"时，先 `head -1` 看第一行，再查 BOM。

### 1.5 工具能力边界表

| 能力 | 实测边界 | 应对 |
|------|---------|------|
| 交互弹窗选项数 | AskUserQuestion 硬限 2-4 个选项 | 超 4 个用交互降级模式（2.2） |
| 内置子智能体类型 | Explore 只读、无弹窗工具 | PreToolUse Hook 强制拦截（2.3） |
| Agent 工具参数 | 不接受模型参数 | 走定义文件绑定（1.1） |

> 边界数值用最小用例实测确认（读平台源码/Schema 亦可），不要凭印象假设。

## 第二章 架构模式库（按约束选型）

### 2.1 两技能拆分模式

**适用**：产物不热加载（1.3）+ 产物可以预先批量生成。

```
技能 A（初始化，一次性）：批量预生成所有产物 → 提示"新会话生效"
技能 B（日常使用）：检测产物已存在 → 直接使用，零创建
```

- 解决"每次用时动态生成 → 必须重启会话"的死循环。
- 日常路径不依赖生成动作，天然规避热加载问题。
- 新增产物时重跑技能 A 即可；技能 B 里保留"产物不存在 → 引导去跑 A"的检测分支。

### 2.2 交互降级模式（选项超限）

**适用**：可选项数量可能超过交互工具上限。

```
第一层：全量文本列表（带编号）直接输出给用户——不受弹窗限制
第二层：弹窗只放 4 个"实际可用的常用项"（从第一步结果里挑，不硬编码）
第三层：Other 自由输入兜底，支持三种玩法：
  - 输入编号 → 展开该组下的子选项
  - 输入关键词 → 服务端搜索后，匹配 ≤4 个再弹窗、1 个直接确认、>4 个继续缩小
  - 输入精确标识 → 直接使用
```

**要点**：弹窗选项必须**从运行时数据里选**，禁止把某台机器的配置硬编码进示例（用户的机器上大概率没有）。

### 2.3 防护闭环模式（标志文件 + 双 Hook）

**适用**：需要在"产物未就绪"时拦截误用，且无法直接查询平台加载状态。

```
生成侧：生成产物成功后写标志文件（含时间戳）
PreToolUse Hook：检测到使用产物 + 标志存在 → exit 2 拒绝，提示正确做法
SessionStart Hook：新会话启动 = 产物已加载 → 清除标志
```

- 语义精确：**同会话拦截、跨会话放行**，无需时间窗口猜测，无会话身份依赖。
- **完整性检查**：文档声称的保护必须端到端验证——本模式曾出现"hook 只读标志、无人写标志"的断链，README 写了保护但保护从未生效。验证法：写标志 → 模拟派发（应 exit 2）→ 清标志 → 再派发（应 exit 0）。
- Hook 副作用要兜底：标志写失败、清理失败都不能影响主流程（try/pass + 日志）。

### 2.4 指纹隔离模式（用户数据红线）

**适用**：插件会在用户目录生成文件，且需要清理/覆盖。

```
生成时：内容嵌入固定指纹串（如 description 含「<插件名> 生成」）
清理时：文件名匹配 + 内容含指纹 → 才删；只有文件名匹配 → 保留并打印提示
覆盖时：目标存在但无指纹 → 跳过不覆盖，警告用户
```

- **红线**：用户自定义的一定不能碰，哪怕文件名长得一模一样。
- 卸载文档里的删除命令也要按指纹过滤（PowerShell `Select-String -Quiet` / bash `grep -l | xargs rm`），不能 `rm router-*` 一刀切。
- 指纹放在用户可见的语义字段里（description），而不是隐藏注释——用户能在设置界面看清来源。

## 第三章 可靠性工程

### 3.1 两层验证模型

```
第 1 层：静态检查（零成本，先跑）
  显式禁用 / 系统禁用原因 / 凭证为空 → 直接判不可用
  只能拦"配置层"问题
第 2 层：真实探测（一次最小请求）
  拦"服务端拒绝"：token 失效、验证码校验、套餐无权益
  静态全绿 ≠ 真的能用
```

### 3.2 探测工程细节（每个细节都踩过坑）

| 细节 | 坑 | 正确做法 |
|------|-----|---------|
| 请求签名 | 默认脚本 UA 被防护拦截（CF error 1010），把可用模型误判为不可用 | 按官方 SDK 标准签名发（UA + x-stainless 头），不用浏览器伪装 |
| 请求体 | 非流式请求要等完整回复，慢模型超时误判 | `stream: true`，读到首包即断，几秒出结论 |
| 判定 | 二值判定（可用/不可用）会误杀慢响应 | 三态：ok / fail（服务端明确拒绝）/ unknown（超时重试 1 次后保留，不判死） |
| 性能 | 逐个串行探测 12 个模型 5 分钟+ | 线程池并发（纯 I/O），总耗时 = 最慢一个 |
| 确定性故障 | 连接拒绝/DNS 失败重试无意义 | 识别 refused/getaddrinfo 立即判 fail，只对超时重试 |
| 成本 | 探测请求本身有费用 | 探测问题选零思考成本的一句话（如"今天周几"），max_tokens 限量 |

### 3.3 文档-实现一致性复核

发布前对 README/文档里每一条"保护/机制"声明，到代码里找对应实现：

- 声称"Hook 拦截 X" → hook 代码里有没有这条分支？触发条件有人写吗？
- 声称"自动检测" → 检测逻辑在哪个函数？谁调用？
- 本次实战抓到的断链：标志文件"只有读没有写"——文档描述的保护从未生效过。
- 修法二选一：补实现（优先，让保护变真）或改文档（降级声明）。

## 第四章 调试方法论（session 排障四步法）

> 场景：用户报"子智能体执行失败"，只给一个 session ID。

```
第 1 步：会话上下文提取
  读会话记录，确认当时发生了什么（任务、派发类型、用户选择）
  注意：记录可能截断，没有报错细节是常态，别在这里下结论

第 2 步：agent 运行档案
  ~/.zcode/cli/agents/sess_<id>/agent_xxx/
  metadata.json：profileId（用了哪个定义）、profileSnapshot（当时绑定的 model）、
                status、error、completedAt - createdAt（失败耗时）
  task.output：子智能体的输出/报错

第 3 步：平台日志挖底层错误
  ~/.zcode/cli/log/zcode-<日期>.jsonl
  grep '"level":"error"' + 时间窗 → "Turn execution failed" 只是包装，
  看 cause 链里的真实错误（如 ProviderBusinessError: captcha verify failed, code 3007）

第 4 步：脱离平台最小复现
  用 python/curl 直接对 provider 发最小请求（复用第 3 步拿到的 baseURL/key/model）
  复现成功 → 平台无关的服务端问题；复现失败 → 平台配置/机制问题
```

**判定纪律**：拿到底层错误码才算找到根因。"可能大概是"不算诊断。

### 4.5 典型错误速查表

| 表面现象 | 底层真相 | 修复动作 |
|---------|---------|---------|
| Agent type not found | 定义是本会话生成的，未加载 | 新建会话；防护见 2.3 |
| agent_missing_frontmatter | 文件首行不是 `---` | 生成器去掉前置注释 |
| 路由到了错误模型 | model 字段用了裸名/slash 格式 | 换平台原生格式（1.2 探测链） |
| Turn execution failed | 看 cause：多为 provider 业务错误 | 按错误码处理（3007=重新授权账号） |
| 探测全挂但模型明明能用 | 防护拦了脚本签名 | 换官方 SDK 标准签名（3.2） |
| 卸载后设置里还有定义 | 只清了 cache，另有 4-5 处独立存储 | 按清单全清（含注册表 JSON、生成物） |
| 更新后还是旧版 | 市场清单有缓存 | 先刷新市场再检查更新，两步都不能跳 |
| 本地改了 cache 但过会儿又变回去 | 市场源回写覆盖 cache | 改源头仓库并推送，不要打本地补丁 |

## 第五章 发布与协作纪律

### 5.1 发布链

```
功能完成 → 泄密扫描 → commit（需要时 squash 成单提交）→ 备份 → 同步运行时 cache → push（需用户逐次授权）
用户侧更新 = 刷新市场缓存 → 检查更新（两步，缺一检测不到新版本）
```

- **push 授权制**：未经用户逐次明确允许不 push。一次授权只覆盖一次。
- **先备份再动刀**：git reset、大改、清理前，整目录（含 .git）备份到版本备份目录。
- commit 信息写"为什么"而不是"改了什么文件"——文件清单 git 自己记得。

### 5.2 泄密红线（提交前扫描）

不入库内容：本地绝对路径、API key/token、供应商真实名称（用户没公开的话）、用户业务数据。

```bash
# 提交前快速扫描
git diff --cached | grep -inE "G:\\\\|C:\\\\Users|apiKey|sk-|eyJ"
```

### 5.3 版本缓存坑

- 用户侧"更新插件"必须两步：刷新市场缓存 → 检查更新。只做第二步永远看到旧版。
- 开发者侧：直接改 cache 目录里的文件是**临时手段**，市场源（git 仓库）刷新时会回写覆盖。正确的持久修改路径：改源仓库 → push → 用户侧刷新。

## 第六章 可复用骨架（直接抄）

### 6.1 目录树

```
<plugin-name>/
├── .zcode-plugin/
│   └── plugin.json          # 插件清单
├── commands/                # 斜杠命令（自动发现）
│   ├── <name>-setup.md      #   初始化命令（对应技能 A）
│   └── <main>.md            #   日常命令（对应技能 B）
├── skills/
│   └── <skill-name>/
│       ├── SKILL.md         # 技能主体（含硬性禁令章节）
│       ├── scripts/         # 核心逻辑（Python，标准库优先）
│       └── references/      # 参考数据
├── hooks/
│   ├── hooks.json           # SessionStart + PreToolUse
│   └── check-*.js           # Node hook 脚本
├── demo/                    # README 截图
├── .doc/                    # PRD / 开发文档（不进市场展示）
├── README.md
└── marketplace.json         # 市场注册（仓库根）
```

### 6.2 各文件必改点

| 文件 | 必改点 |
|------|--------|
| plugin.json | name（小写开头 ^[a-z0-9][a-z0-9._-]{0,127}$）、version、skills/commands/hooks 路径 |
| commands/*.md | frontmatter description 一句话说清何时用；正文固定三段：先加载技能 → 执行步骤 → $ARGUMENTS |
| SKILL.md | name/description/when_to_use + 脚本定位规则 + 流程步骤（强制化）+ 禁止行为章节 |
| hooks/hooks.json | SessionStart（清标志）+ PreToolUse（matcher 匹配目标工具） |
| hook 脚本 | 读 stdin JSON → 判定 → exit 0/2；日志 append 到 %TEMP% 方便排障 |

### 6.3 核心代码片段索引（见 scripts/router.py 实现）

- `_provider_usable()`——静态三关检查（禁用/系统禁用原因/凭证为空）
- `probe_model()`——SDK 标准签名 + 流式首包 + 三态判定 + 确定性故障免重试
- `_probe_all()`——ThreadPoolExecutor 并发，max_workers=min(n,16)，as_completed 收集
- `_is_plugin_generated()` / `GENERATED_MARKER`——指纹判定
- `_write_flag()`——标志文件写入（对应 hook 的 SessionStart 清除）

### 6.4 SKILL.md 强制化写法

```
1. 流程步骤用"步骤 1→2→3"编号，每步写明"必须/禁止"
2. 开头放一段🚨硬性规定：禁止跳过流程、禁止用替代品糊弄、禁止假设用户意图
3. 结尾放🚫禁止行为清单，逐条对应历史上实际发生过的违规
4. 脚本路径规则：以 SKILL.md 所在目录为基准拼接，禁止凭记忆猜安装层级
5. 示例中的具体值（模型名、provider 名）一律标注"仅为格式示例"
```
